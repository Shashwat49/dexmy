# Dexmy package roadmap audit and implementation status

Audit date: 2026-11-28. Audited `origin/main` at `59daf01` (the merge containing PR #118). The source checkout does not contain the referenced 229-row roadmap document; this matrix reconciles the 14 phases and acceptance details supplied in the task, not an unavailable task-ID list.

## Current architecture and compatibility decisions

- Production `dexmy` serves the FastAPI app from `/backend`; Railway starts `uvicorn app.main:app` directly and does not run migrations on startup. Browser auth uses HttpOnly access/refresh cookies; cookie-authenticated mutations validate CSRF and the exact allowed Origin. Public catalogue endpoints are unauthenticated.
- PostgreSQL/SQLAlchemy models hold `PackagePlan`, `Payment`, `StudentPackage`, and `PackageCreditLedger`. `package_plan_subjects` is the existing optional allow-list. PR #118's booking-time entitlement selection and debit validation remain the authority for booking; package schedules and teacher assignment remain on their existing paths.
- Package checkout already snapshots the plan class count and total into one `Payment`, validates plan currency and selected subject, signs/verifies provider events, checks provider amount/currency, and locks payment activation. It supports Razorpay/INR and Stripe/USD only. Selected subject was validated but not saved, so it could not scope a later entitlement. This change saves it for new purchases and keeps the columns nullable so legacy purchases retain their existing plan-subject behavior.
- `PackagePlan.price` is the configured per-class amount; `Payment.amount` is the persisted checkout total. Existing `backend/sql_migrations/002_package_pricing.sql` specifies INR rates of ₹2,000/₹1,950/₹1,900/₹1,850 for 25/50/75/100 classes and USD rates of $20/$19.50/$19/$18.50. For example, 25 INR classes total ₹50,000. No 25% discount is present in this configuration, so none is added. No FX rates or GBP/EUR provider capability are present, so no conversion or unsupported currency is invented.
- Invoices are generated from a single `Payment` on demand; class reminders already use Resend/SMTP. The app has no purchase-email outbox, no board/exam catalogue, no persistent cart/order, and no WhatsApp scheduling-notice state.
- Protected Meet recording, class-record submission, classroom, booking completion, and background reminder paths were not changed. The existing account-specific package display branches in `StudentDashboard.jsx` and the historical unlimited-package migration remain flagged for data-owner reconciliation; changing those without reconciling existing real entitlements could alter balances.

## Migration and rollout safety

`backend/sql_migrations/008_student_package_subject_scope.sql` is additive and repeatable; the matching Alembic revision is `20261128_student_package_subject_scope`. Existing purchases stay `NULL` and therefore keep current package-plan subject compatibility. Apply and verify the schema change in a disposable/local database first. The production Railway service has no automatic migration step, and application queries will require these columns after this code is deployed. Because production SQL execution is explicitly prohibited for this task, do not merge/deploy this branch until the database owner separately approves and applies the migration. No SQL was run against either Supabase project.
